# Established spec-driven AI development workflows

Research performed 2026-11-11. Started with the available web-search integration (provider not disclosed; not claimed to be Google), then fetched official docs/repos. Repository `main` and website pages are mutable snapshots, not pinned releases. Kiro pages explicitly display update dates below; undated pages must not be described as newly published in November 2026. Findings describe documented behavior, not independently measured reliability. No agent/config files were changed.

## GitHub Spec Kit: artifacts, gates, existing code, lifecycle

### Takeaway
Spec Kit separates behavioral intent from implementation planning and executable tasks, with project-wide guardrails and explicit consistency/completeness checks. The fetched documentation is broader and more flexible than the common characterization of an immutable waterfall workflow. — [Official quickstart](https://github.github.io/spec-kit/quickstart.html); [command reference](https://github.github.io/spec-kit/reference/agentic-sdd.html)

### Cited Findings
- **Artifacts/order:** establish a constitution once per project; then specify → plan → tasks → implement → converge. The fuller path adds clarify before plan, checklist after plan, and analyze after tasks. `spec.md` is what/why, `plan.md` is technical implementation approach, and `tasks.md` is dependency-ordered work. Planning generates supporting design artifacts; not everything must live in a single giant spec. — [Quickstart](https://github.github.io/spec-kit/quickstart.html); [reference](https://github.github.io/spec-kit/reference/agentic-sdd.html)
- **Human review versus mechanical gates:** the quickstart says invoke each skill separately and review before continuing. The reference says commands are designed for order but only specify is strictly required before plan; clarify/checklist/analyze are optional quality gates. Thus “all phases rigidly enforced” overstates the official description. Implementation reads checklist states and asks before proceeding with unchecked items; it must not change their markers. Custom checklists are reviewer-owned requirements-quality artifacts, not task-completion lists. The built-in requirements checklist has a separate specify/clarify-maintained lifecycle. — [Quickstart](https://github.github.io/spec-kit/quickstart.html); [reference](https://github.github.io/spec-kit/reference/agentic-sdd.html)
- **Precision:** clarify asks up to five targeted questions per run and folds answers into the spec; analyze is read-only across spec/plan/tasks and reports inconsistencies. Task generation groups work by dependencies and user stories; tests are included when requested, so “uses Spec Kit” alone does not guarantee a test-first process. — [Reference](https://github.github.io/spec-kit/reference/agentic-sdd.html)
- **Existing code:** initialize in place, inspect generated changes, capture guardrails from repository evidence, and choose the next bounded change. Initialization neither rewrites the application nor infers its existing specification. Code remains implementation context; explicitly specify compatibility boundaries and reuse architecture, dependencies, and testing conventions. Do not first reverse-specify the whole system unless that inventory is itself the deliverable. — [Existing-project guide](https://github.github.io/spec-kit/how-to/existing-projects.html)
- **Change lifecycle:** distinguish a defect against agreed intent from a requested intent change. Review artifacts, implementation, tests, and maintained decisions; revise the owning spec/plan/tasks and rerun analysis. Core does not automatically reconcile those documents. Converge assesses code against agreed artifacts and can only append missing work to tasks; it cannot rewrite requirements to bless the implementation. Repeat implement/converge until complete, then review/PR. Retention is a separate team decision, not an automatic archival convention. — [Evolving specs](https://github.github.io/spec-kit/how-to/evolving-specs.html)
- **Scope/limit:** the fetched README also offers independent bug-fixing and idea-assessment processes; SDD is not a prerequisite for every repair or investigation. Large implementations can be staged to avoid context overload. — [Official repository](https://github.com/github/spec-kit); [reference](https://github.github.io/spec-kit/reference/agentic-sdd.html)

### Inferences
- Borrow the separation of intent, approach, and tasks, plus a read-only consistency check. Do not import every ceremony into small changes.
- For the planner, make human authorization a recorded explicit event rather than inferring it from a document's existence or agent-checked task boxes.

### Gaps
- No benchmark evidence was collected that these gates improve delivery quality. These mutable official pages expose no publication/update date in the fetched text; do not assign a release version or November publication date.

## Amazon Kiro: artifacts, gates, existing code, lifecycle

### Takeaway
Kiro provides the clearest documented staged human-review model, but its artifact split is requirements/design/tasks—not simply human document versus agent document. Current fetched docs also include Design-First and Quick Spec, so older “always requirements-first with mandatory gates” summaries are incomplete. — [Feature Specs](https://kiro.dev/docs/specs/feature-specs/); [best practices](https://kiro.dev/docs/specs/best-practices/)

### Cited Findings
- **Artifacts/order:** feature specs use `requirements.md`, `design.md`, and `tasks.md`. Requirements-First generates user stories, acceptance criteria, functional behavior, edge/error cases; after confirmation it generates architecture, component interactions, interfaces/models, error handling, and testing strategy; tasks contain expected outcomes, dependencies, and required/optional work. The user reviews requirements, design, and task breakdown before implementation. — [Requirements-First](https://kiro.dev/docs/specs/feature-specs/requirements-first.md)
- **Testable requirements:** Kiro uses EARS-style `WHEN [condition/event] THE SYSTEM SHALL [behavior]` notation. This is an aid to clarity, traceability, and tests, not an executable proof of correctness. — [Feature Specs](https://kiro.dev/docs/specs/feature-specs/)
- **Alternative order:** Design-First is design → requirements → tasks, suitable for existing designs, strict nonfunctional constraints, or feasibility exploration. Requirements-First is requirements → design → tasks. Quick Spec creates the same three artifacts without intermediate approval gates for well-understood work. Standard Feature Specs are recommended where iteration, unfamiliarity, compliance, or explicit checkpoints matter. — [Feature Specs](https://kiro.dev/docs/specs/feature-specs/); [best practices](https://kiro.dev/docs/specs/best-practices/)
- **Existing context:** existing architecture documents/diagrams can seed Design-First; external requirements can be imported manually or through MCP. For existing code, Sync Files or an explicit code scan can mark already-implemented tasks. The docs recommend feature-focused specs rather than one document for the entire codebase. — [Best practices](https://kiro.dev/docs/specs/best-practices/)
- **Change lifecycle:** Requirements-First revisions update requirements, then design, then Sync Files to generate corresponding tasks; Design-First reverses the first two. Keep specs version-controlled alongside code. Switching workflow types requires creating a new spec and copying relevant material. — [Best practices](https://kiro.dev/docs/specs/best-practices/)
- **Preservation:** Bugfix Specs separately capture unchanged behavior using `SHALL CONTINUE TO`; straightforward one-line fixes can stay in chat. Feature Specs are not recommended for exploratory coding without clear goals or as the generic bug-fix workflow. — [Best practices](https://kiro.dev/docs/specs/best-practices/); [Feature Specs](https://kiro.dev/docs/specs/feature-specs/)
- **Source dates:** Feature Specs displays “Page updated: August 4, 2026”; best practices displays September 25, 2026. These are page-level dates, not necessarily feature launch dates. — [Feature Specs](https://kiro.dev/docs/specs/feature-specs/); [best practices](https://kiro.dev/docs/specs/best-practices/)

### Inferences
- A high-level human design decision can precede the full low-level execution contract, but requirements and success criteria still need to constrain the technical work; do not let implementation feasibility silently redefine the user's desired outcome.
- Put compatibility and unchanged behavior explicitly in the planner's execution contract, especially for existing systems.

### Gaps
- The inspected pages do not establish an OpenSpec-like mandatory archive/merge lifecycle. Do not invent one. Product surface/model restrictions in competing tools' comparison copy were not verified and should not be repeated as fact.

## OpenSpec: artifacts, gates, existing code, lifecycle; implications for the planner

### Takeaway
OpenSpec provides the strongest model for separating durable behavior contracts from temporary change plans, with explicit deltas and archival history. It deliberately avoids rigid phase gates, so a hard human-approval boundary would be a local policy layered on top—not a native universal guarantee. — [Official concepts](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md); [workflows](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/workflows.md)

### Cited Findings
- **Artifacts:** durable `openspec/specs/<domain>/spec.md` holds current agreed behavior. An active change folder contains `proposal.md` (why/scope/high-level approach), delta `specs/` (behavior changes), `design.md` (technical decisions), and `tasks.md` (checklist). Specs are behavior contracts with requirements and scenarios; internal symbols, libraries, and implementation steps belong in design/tasks, not behavior specs. — [Concepts](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md)
- **Order is a graph, not a rigid linear chain:** the displayed standard flow is proposal → specs → design → tasks → implement, but the documented schema lets specs and design both depend on proposal, with tasks depending on both. Dependencies enable artifact generation; they are not human approval gates. Artifacts can be revised as discoveries arise. — [Concepts](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md)
- **Human review:** `/opsx:propose` drafts planning artifacts for review; `/opsx:apply` implements. Expanded commands offer `/opsx:new` plus `/opsx:continue` for stepwise artifact creation or `/opsx:ff` for all-at-once drafting. `/opsx:explore` investigates existing code without writing code and writes other artifacts only when requested/accepted. — [Workflows](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/workflows.md)
- **Brownfield:** deltas specify ADDED, MODIFIED, and REMOVED requirements rather than restating the system. Domain specs and separate change folders support bounded changes and concurrent planning, but the docs also discuss detecting overlapping spec changes during bulk archive; do not promise conflict-free concurrency. — [Concepts](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md); [workflows](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/workflows.md)
- **Lifecycle:** implement tasks, optionally verify completeness/correctness/coherence, sync delta specs into durable specs, then archive the change with its rationale/history. Agent-driven archive can offer sync or allow skipping; the CLI archive path validates and applies deltas. Verification does not block archive, and incomplete tasks trigger warnings rather than an absolute prohibition. Thus archive alone is not evidence of verified completion. — [Workflows](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/workflows.md)
- **Changing intent:** update the same change for refined execution, narrowing scope, and learning-driven corrections; start a new change when the intent fundamentally changes or work becomes independently deliverable. Use progressive rigor: lightweight behavior-first acceptance checks for most changes, fuller contracts for migrations, security, APIs, or cross-team work. — [Workflows](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/workflows.md); [concepts](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md)

### Inferences
- **Recommended synthesis, not a claim that any framework mandates it:** use one change package with two audience-specific artifacts: (1) a short human decision brief, (2) a precise agent execution contract, with a task checklist as a section or third artifact only when needed. Two audiences need not mean only two logical layers: intent/behavior, implementation design, and work breakdown remain distinct.
- **Suggested flow:** inspect current code/context → draft high-level outcomes/options/scope/non-goals/risks/acceptance examples → obtain explicit human approval → elaborate the technical contract and dependent tasks → check consistency with the approved brief → hand off for execution → verify against acceptance criteria → retain useful requirements/decisions and archive transient work.
- **Avoid approving fiction:** do enough repository investigation and feasibility work before human approval to offer credible options, but defer exhaustive file/symbol/task detail to the agent-facing contract. Human approval should cover behavior, scope, important architecture/tradeoffs, and risk—not a premature source-file inventory.
- **Precise execution contract:** carry requirement IDs, observed baseline and evidence, invariants/compatibility, interfaces/data/error cases, affected implementation areas, dependencies/order, verification commands/results expected, completion criteria, and escalation rules. Trace tasks/tests to the same acceptance criteria rather than duplicating competing requirements.
- **Reapproval policy:** ordinary implementation refinements can update the execution contract; changes to approved scope, behavior, compatibility, architecture commitments, or material risk return to the human. Preserve the original approval and summarize the decision delta; never silently change the brief to match code.
- **Do not equate three different gates:** human authorization, artifact-quality/consistency checks, and implementation verification answer different questions. A generated spec, checked task, or archive move proves none of the others.

### Gaps
- OpenSpec sources here are undated mutable `main` documents, not a version-pinned release. The repository README and workflow doc differ in some default-profile command listings; rely on the detailed workflow for semantics, and avoid presenting a version-specific command inventory as universally installed. No empirical comparison establishes one framework as best; the proposed planner structure is a reasoned synthesis.
