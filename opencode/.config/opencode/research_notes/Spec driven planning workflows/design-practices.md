# Established design practices for two-part agent planning

Research date: 2026-11-11. Scope: human-facing design and decisions versus agent-facing implementation specifications; not a recommendation for Google tooling. Findings below distinguish source claims from proposed application. No agent/config files changed.

## 1. What can we borrow from Google's design practices?

### Takeaway
Google's published practices support separating a readable argument about goals, alternatives, and tradeoffs from exhaustive implementation detail. They do not establish that a particular two-file agent workflow is superior, nor that using Google's tools is necessary. [Software Engineering at Google, chapter 10](https://abseil.io/resources/swe-book/html/ch10.html); [Malte Ubl, Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)

### Cited Findings
- **Strongest institutional account:** the Google-authored book says most teams require an approved design doc before a major project. Good docs cover goals, implementation strategy, key decisions and tradeoffs, plus alternative designs' strengths and weaknesses. Templates surface security, privacy, internationalization and storage concerns for expert review. This is explicitly about major projects, not every bug fix. [Book, Design Docs subsection](https://abseil.io/resources/swe-book/html/ch10.html)
- **Audience and purpose matter:** the same chapter advises identifying a primary audience, keeping documents short, giving each document a singular purpose, and not mixing documentation types. It explicitly distinguishes decision-maker persuasion from detailed instructions for other readers. [Book, Know Your Audience / Documentation Types](https://abseil.io/resources/swe-book/html/ch10.html)
- **Ownership and canonical sources matter as much as templates:** documents should have owners, version control, reviews, tracked defects and periodic evaluation. Conflicting documentation needs a designated canonical source; duplicates should be consolidated or deprecated. Collaborative Google Docs can be useful early, but stable historical records should move somewhere permanent with clear ownership and version control. [Book, Documentation Is Like Code / Documentation Philosophy](https://abseil.io/resources/swe-book/html/ch10.html)
- **Useful practitioner elaboration, not official company policy:** Malte Ubl's first-person account describes relatively informal design docs: context/scope, goals/non-goals, design, alternatives and cross-cutting concerns. It says to focus on tradeoffs rather than copying full API or schema definitions; code is rarely appropriate except for novel algorithms, and prototypes can be linked. [Ubl, 2020](https://www.industrialempathy.com/posts/design-docs-at-google/)
- **Scale the process:** Ubl suggests 1–3 page mini-docs for incremental improvements, versus roughly 10–20 pages for larger projects. These are his heuristics, not a mandatory template. He argues a design doc is often unnecessary if there is no meaningful ambiguity or tradeoff and warns that formal review meetings can become bottlenecks. [Ubl, Length / When not to write / Review](https://www.industrialempathy.com/posts/design-docs-at-google/)
- **Design changes during implementation are expected:** Ubl recommends updating the design before shipping when assumptions prove wrong. The book similarly suggests comparing the approved design's goals with the product before launch and adjusting either as appropriate. [Ubl, Implementation and iteration](https://www.industrialempathy.com/posts/design-docs-at-google/); [Book, Design Docs](https://abseil.io/resources/swe-book/html/ch10.html)

### Inferences
- **Proposed two-part split:** human design = problem, outcomes, non-goals, important constraints, selected approach, alternatives, consequences, risks and open decisions. Agent execution spec = repository-grounded facts, precise interfaces/invariants, work packages, dependencies and verification instructions. This extends Google's audience/purpose separation; it is not a claim that Google uses this exact agent workflow. [Basis: book](https://abseil.io/resources/swe-book/html/ch10.html)
- **Separate audiences, not “nontechnical versus technical”:** architecture, privacy, compatibility and migration choices can belong in the human design when they affect the decision. Source-file inventories and mechanical task sequencing normally belong in the execution spec. Avoid stripping decision-relevant technical substance from the human artifact. [Basis: Ubl's tradeoff emphasis](https://www.industrialempathy.com/posts/design-docs-at-google/)
- **Lightweight default:** for a reversible, obvious change, use a short intent/constraints/acceptance note and a small task list; create a fuller design only when ambiguity, cross-cutting risk or coordination warrants it. A rigid two-large-doc requirement would contradict the proportionality advice. [Basis: Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/)

### Gaps
- These public accounts establish engineering practices, not measured AI-agent outcomes. No comparative experiment found here demonstrates that separating human design from execution specs improves speed, correctness or review quality.
- The book and Ubl article are dated accounts. Neither proves that all Google teams follow one uniform process today. Do not generalize the practitioner's page counts or privacy-policy details into current mandatory Google policy.

## 2. How do RFCs, ADRs, acceptance criteria and traceability fit together?

### Takeaway
Use proposal review to settle important choices, decision records to preserve why, and acceptance evidence to check behavior. These are different roles, not necessarily four mandatory documents: the lightest useful workflow can combine roles and link to existing tests. [Rust RFC process](https://github.com/rust-lang/rfcs/blob/main/README.md); [Nygard ADRs](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions); [Cucumber guidance](https://cucumber.io/docs/bdd/better-gherkin/)

### Cited Findings
- **RFC as a proposal/decision process (concrete example, not universal definition):** Rust uses RFCs for substantial changes to build stakeholder confidence and consensus; ordinary bug fixes and documentation improvements can use normal PR review. The process requires motivation, impact, drawbacks and alternatives, followed by revision and a final decision. [Rust RFC README](https://github.com/rust-lang/rfcs/blob/main/README.md)
- **Acceptance is not execution or delivery:** Rust explicitly says an active RFC neither guarantees eventual merge nor assigns implementation priority or an implementer. Each accepted RFC has an implementation tracking issue. Substantial subsequent changes generally need a new RFC linked from the old one. [Rust RFC lifecycle](https://github.com/rust-lang/rfcs/blob/main/README.md)
- **ADR as a durable, narrow decision record:** Michael Nygard proposes one short record per architecturally significant decision, including title, context, decision, status and consequences. Consequences include negative and neutral effects, not just benefits. Status distinguishes proposed from accepted, deprecated and superseded; old records remain with replacement links. His suggested length is one or two pages. [Original ADR article, 2011](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- **Do not overstate the distinction:** ADRs can be proposed before acceptance; RFCs can preserve history after acceptance. The useful difference is primary purpose and granularity (deliberation on a change versus recording a significant decision), not a universal rule that one must precede code and the other follow it. [Nygard statuses](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions); [Rust lifecycle](https://github.com/rust-lang/rfcs/blob/main/README.md)
- **Acceptance criteria should describe behavior:** Cucumber advises describing what the system does rather than procedural UI steps. Declarative scenarios expose intent while step definitions contain implementation mechanics, reducing coupling when UI details change. [Writing better Gherkin](https://cucumber.io/docs/bdd/better-gherkin/)
- **“Executable specification” has a concrete meaning in BDD:** Gherkin examples are executed via matching step-definition code; Then steps compare actual and expected observable outputs. Free-form feature descriptions are ignored at runtime. Merely writing Given/When/Then prose does not create executable verification. [Gherkin reference](https://cucumber.io/docs/gherkin/reference)
- **Heavyweight traceability precedent:** NASA NPR 7150.2D requires documented acceptance criteria (§3.1.5) and maintained bidirectional links among requirements, design, code, verification and nonconformances according to software classification (§3.12). Its requirements are contextual to NASA, not a general mandate for ordinary apps. [NASA directive](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=Chapter3)
- **Generated code is not exempt:** NASA's automatic-generation requirements include tool/input/output configuration management, scope limits, manual-edit policies and verification of generated code using the same standards as handwritten code (§3.8). This is useful assurance precedent, not evidence that LLM generation meets those requirements. [NASA directive](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=Chapter3)

### Inferences
- **Suggested minimum contract:** assign stable IDs only to meaningful acceptance criteria and consequential decisions. Each execution work package references relevant IDs, and completion records link to actual test results or explicit manual evidence. This applies traceability in a smaller form without importing NASA's full process. [Basis: NASA traceability](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=Chapter3)
- **Canonical authority by concern:** human-approved design owns intent/constraints/decisions; maintained tests or formal contracts own machine-checkable behavior; execution spec owns the current implementation plan. Link rather than duplicate. A contradiction should trigger explicit reconciliation, not let the agent silently choose whichever document seems newer. [Basis: Google canonical documentation](https://abseil.io/resources/swe-book/html/ch10.html)
- **Lightweight approach:** one short design with decisions and acceptance IDs; one execution note referencing them; existing tests as evidence. **Heavier approach:** RFC review for cross-team/API/migration changes, ADRs for durable architectural choices, maintained requirement-to-verification mapping and independent assurance for high-risk work. Additional records buy auditability and coordination but add maintenance and review costs. [Basis: Rust RFC scope](https://github.com/rust-lang/rfcs/blob/main/README.md); [NASA](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=Chapter3); [Ubl review overhead](https://www.industrialempathy.com/posts/design-docs-at-google/)
- **Do not demand Gherkin everywhere:** precise bullet criteria plus ordinary automated tests can preserve the behavior/implementation separation. Adopt a BDD runner when the shared executable language is worth maintaining its step-definition layer. [Basis: Cucumber runtime model](https://cucumber.io/docs/gherkin/reference)

### Gaps
- RFC and ADR terminology varies across organizations; no single universal boundary or mandatory combination is established by these sources.
- The optimal traceability granularity for this user's work remains a decision: criterion-to-test may suffice; task-to-file-to-test mapping is more costly and not justified automatically.
- Behavioral tests alone do not settle architectural quality, accessibility, security or operational readiness. The specific acceptance evidence and reviewer for these concerns must be chosen for the project; Google's expert review practice is one precedent, not a complete solution. [Google review coverage](https://abseil.io/resources/swe-book/html/ch10.html)

## 3. What does critical SDD analysis imply for the proposed workflow?

### Takeaway
Treat spec-driven planning as a proportional, iterative working agreement, not an assurance mechanism by itself. The most important unresolved issue is whether specs expire after a change or remain maintained feature contracts; the answer changes ownership, drift handling and the amount of process required. [Birgitta Böckeler, 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

### Cited Findings
- **Correct attribution:** the relevant article on Martin Fowler's site is by Birgitta Böckeler, dated 15 October 2025; it is not authored by Martin Fowler. She distinguishes spec-first (write before implementation), spec-anchored (maintain for future feature evolution), and spec-as-source (humans edit specs, not generated code). She notes maintenance intent is often vague. [Understanding Spec-Driven-Development](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **Distinguish context from task specifications:** Böckeler separates codebase-wide memory/rules from specs relevant to particular functionality. This supports not putting every task's execution instructions into global agent rules. [Same article, What is a spec?](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **Observed review overhead:** in her trials, a small Kiro bug fix expanded into four user stories and sixteen acceptance criteria; spec-kit produced many repetitive markdown artifacts. She questions a single workflow for all change sizes and asks for a better spec review experience. These are practitioner observations, not benchmark results or claims about current product versions. [Observations and questions](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **False control and brownfield failures:** she observed agents ignoring instructions despite templates/checklists; one generated duplicates of existing classes after treating research descriptions as instructions for new code. Larger context windows did not ensure compliance. [False sense of control?](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **Functional/technical separation remains hard:** her trials showed confusion over when technical detail belongs in a functional spec; she questions target users and problem sizes. She favors small iterative steps over excessive up-front specification. [Functional vs technical / target user](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **Natural-language flexibility has a price:** she compares spec-as-source to model-driven development, noting loss of deterministic generation and some tooling support for validating complete, consistent specs. She asks whether approaches might combine inflexibility with nondeterminism; this is an explicit concern, not proven inevitable failure. [Learning from the past](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **Not anti-spec:** she says she personally often crafts specs before coding and finds spec-first valuable in many situations. Her critique concerns ambiguity, tool/process fit and overhead, not a conclusion that all specifications are bad. [Conclusions](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

### Inferences
- **Recommended pilot, not rollout:** try a two-part format on one moderately ambiguous change. Compare human review time, clarification rounds, unplanned changes and acceptance failures against the current workflow. Keep only sections that materially influence decisions or execution. This is a proposed experiment, not a source-reported result. [Motivation: Böckeler's evaluation limitations](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **Implementation-slice loop:** approve intent and significant choices; ground the next small execution slice in the repository; implement; verify against agreed criteria; update the plan and escalate material design changes. This reconciles design review with discovery rather than pretending approval eliminates uncertainty. [Basis: Ubl implementation iteration](https://www.industrialempathy.com/posts/design-docs-at-google/); [Böckeler small steps](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- **Failure modes and concrete safeguards:**
  - Review theater / generated prose volume: keep the human artifact concise and require meaningful tradeoffs rather than template completion. [Basis: Ubl](https://www.industrialempathy.com/posts/design-docs-at-google/); [Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
  - Spec drift / conflicting documents: name owners, canonical sources and lifecycle; change docs alongside code or mark superseded. [Basis: Google ownership](https://abseil.io/resources/swe-book/html/ch10.html); [Nygard supersession](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
  - Accidental redesign / duplicate implementation: label repository observations as existing facts separately from proposed changes and require reinspection before execution. [Basis: Böckeler brownfield example](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
  - Checkbox completion mistaken for correctness: require linked verification evidence and inspect the code; don't call prose “executable” unless an actual runner validates it. [Basis: Böckeler compliance concerns](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [Cucumber execution semantics](https://cucumber.io/docs/gherkin/reference)
  - Early implementation lock-in: keep observable outcomes separate from mechanical procedures; record technical constraints deliberately rather than smuggling them into user stories. [Basis: Cucumber behavior guidance](https://cucumber.io/docs/bdd/better-gherkin/)
  - Approval misread as authorization/delivery: track design accepted, ready to execute, implemented, verified and released as distinct states. This adapts Rust's explicit separation between RFC acceptance and implementation. [Basis: Rust](https://github.com/rust-lang/rfcs/blob/main/README.md)

### Gaps
- Decisions the parent should surface before choosing a workflow: (1) change-scoped specs or enduring feature contracts; (2) who may change approved intent and when reapproval is required; (3) advisory task prose versus mechanically checked contracts; (4) risk threshold for full design/RFC review; (5) evidence required to claim acceptance; (6) owner responsible for reconciliation after code changes. Sources motivate these decisions but cannot choose them for this user.
- No reliable universal superiority or productivity claim is warranted from these sources. Google's practices are organizational experience; the SDD critique is one expert's bounded 2025 exploration. Tool details may have changed since those trials.
