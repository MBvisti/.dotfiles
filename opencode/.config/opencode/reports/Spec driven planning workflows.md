# Make approved intent guide agent execution

**Improve the existing two-stage planner rather than replace it with an SDD framework.** The current planner already requires a high-level human approval followed by a separate, conversation-independent execution specification; the opportunity is to make their relationship easier to validate and maintain. Keep the human document focused on outcomes, consequential choices and tradeoffs, while the agent specification supplies repository-grounded constraints, bounded work and verification. Borrow behavioral precision from Spec Kit and Kiro, change-lifecycle ideas from OpenSpec, and audience discipline from Google's published design-document practices. Add lightweight traceability and explicit readiness/change rules rather than more mandatory documents. This is a research-backed recommendation, **not an approved proposal**; no planner or configuration changes were made, and choices about permanent feature specs, artifact conventions and process thresholds remain open.

## The current planner already has the right boundary

**Observed local practice:** the inspected planner asks the human to approve goals, non-goals, approach, important decisions, work streams, acceptance criteria and risk. It explicitly excludes unsolicited source-file inventories from that review. After approval, it must produce a separate durable specification for an orchestrator without access to the conversation, including identified work items, dependencies, ownership, verification and escalation. Approval alone is expressly insufficient for handoff. These are written instructions, not evidence that a live execution follows them. ([Current planner](../agents/planner.md))

The strongest existing safeguards should survive any revision: distinguish observations from assumptions, revalidate mutable repository state, preserve regression guarantees, require complete proposed agent definitions when those are the subject of a change, and keep consequential-action permissions separate from plan approval. The planner also already requires returning material changes in direction to the human, without demanding a second high-level approval merely to elaborate implementation details. **The missing emphasis is traceability and lifecycle, not another planning phase.** Stable acceptance identifiers, approval tied to the reviewed version, explicit handling of contradictions and a clear retirement/maintenance policy are not prescribed today. ([Current planner](../agents/planner.md))

**Recommendation:** preserve the two audiences and strengthen the contract between them. Every approved outcome should map to execution work and acceptance evidence; every work item should stay inside an approved outcome or necessary enabling work. Before calling the package ready, perform a read-only consistency check across the approved design, agent specification and intended verification. Do not equate a more elaborate template with runtime enforcement: the inspected orchestrator also accepts direct user requests, so planner-specific readiness guarantees cannot simply be assumed for every execution route. ([Current orchestrator](../agents/orchestrator.md); [Local workflow analysis](../research_notes/Spec%20driven%20planning%20workflows/current-workflow.md))

## Published approaches offer complementary pieces, not a universal winner

**Sourced practice:** Google's engineering book distinguishes documents by audience and purpose, describes approved design documents for major projects, and emphasizes goals, implementation strategy, alternatives and tradeoffs. It also treats documentation as owned, reviewed, maintained engineering work. Malte Ubl's first-person account adds useful guidance about concise mini-docs and avoiding unnecessary design ceremony, but it is a practitioner account—not a uniform, current Google policy. Neither source establishes the superiority of a particular two-document AI workflow. ([Software Engineering at Google, documentation](https://abseil.io/resources/swe-book/html/ch10.html); [Ubl, Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/))

| Approach | Documented distinction and lifecycle | Useful borrowing for this planner | Limit or cost |
|---|---|---|---|
| Google-style design documents | Explain goals, consequential design choices, alternatives and tradeoffs to a defined audience; maintain durable records. | Make Part 1 a decision argument, not a worker checklist. | Organizational practice, not an agent execution protocol. ([Book](https://abseil.io/resources/swe-book/html/ch10.html)) |
| GitHub Spec Kit | Separates what/why, technical planning and dependency-ordered tasks; offers clarification and cross-artifact analysis, plus implementation/convergence workflows. | Separate behavior from mechanics and check consistency before handoff. | Not all quality gates are mandatory; test-first work is not guaranteed simply by adopting the tool. ([Quickstart](https://github.github.io/spec-kit/quickstart.html); [Command reference](https://github.github.io/spec-kit/reference/agentic-sdd.html)) |
| Amazon Kiro | Feature specs separate requirements, design and tasks; supports Requirements-First, Design-First and Quick Spec with differing review cadence. | Make edge cases, unchanged behavior and acceptance criteria explicit; vary ceremony with uncertainty. | Its three logical artifacts do not directly equal two audience-specific documents; Quick Spec omits intermediate approval gates. ([Feature specs](https://kiro.dev/docs/specs/feature-specs/); [Best practices](https://kiro.dev/docs/specs/best-practices/)) |
| OpenSpec | Separates durable behavior specs from change proposals, behavior deltas, design and tasks; supports syncing and archiving changes. | Distinguish enduring contracts from transient execution plans and record change deltas. | Artifact dependencies are not human approval gates; archival alone does not prove verified completion. ([Concepts](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md); [Workflows](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/workflows.md)) |

**Recommendation:** borrow these mechanisms without adopting a framework yet. Spec Kit is the closest reference for intent→design→tasks consistency; Kiro offers clear staged review and concise behavioral notation; OpenSpec is especially relevant if the user wants maintained feature contracts rather than one-change specifications. Framework adoption would introduce conventions and maintenance work beyond the immediate planner improvement. The researched documentation describes available approaches, not comparative reliability or productivity measurements. Pages and repository branches are mutable snapshots checked during research on November 11, 2026, not version-pinned guarantees. Research began with the available web-search integration; its provider was not disclosed, so it should not be represented as a Google search.

## Two audiences still need three distinct logical layers

**Sourced practice:** behavior requirements state what must be observable, design explains how and why the system will satisfy them, and execution tasks organize the work. Spec Kit and Kiro make these separations explicit. Cucumber similarly recommends describing behavior rather than procedural UI mechanics. A sentence written as Given/When/Then or an EARS-style requirement improves precision but is **not automatically executable verification**; Cucumber scenarios need matching step definitions and a runner. ([Spec Kit reference](https://github.github.io/spec-kit/reference/agentic-sdd.html); [Kiro feature specs](https://kiro.dev/docs/specs/feature-specs/); [Cucumber behavior guidance](https://cucumber.io/docs/bdd/better-gherkin/); [Gherkin runtime model](https://cucumber.io/docs/gherkin/reference))

For example, “When a save fails, retain the user's unsaved input and expose a retry” is a behavioral requirement. “Use a durable local draft with explicit synchronization states” is a design choice with storage and privacy consequences. “Implement the draft lifecycle, then verify failure and recovery cases” is execution work. **Two documents should not collapse these three concerns.** Decision-relevant architecture belongs in the human document when it changes tradeoffs; detailed interfaces, mechanical sequencing and worker instructions belong in the agent specification.

**Recommended sample headings—not a selected template:** the following organizes the current planner's obligations without adding another approval stage. Headings describe responsibilities rather than a prescribed artifact directory or schema.

```markdown
# Part 1 — Human design and decision brief
## Problem, evidence and desired outcomes
## Scope, non-goals and constraints
## Proposed approach, alternatives and tradeoffs
## Acceptance criteria and behavior to preserve
## Work streams, dependencies and major risks
## Open decisions and approval scope

# Part 2 — Agent execution specification
## Approved authority, baseline and prerequisites
## Requirements, invariants and acceptance mapping
## Technical design and implementation boundaries
## Work items, dependencies and ownership
## Verification, evidence and review gates
## Escalation, change control and completion
```

**Recommendation:** assign stable IDs to meaningful acceptance criteria and link each work item and verification result to them. Keep the human-approved intent canonical; the execution spec elaborates rather than silently rewrites it. Reuse existing tests and contracts instead of copying their contents into competing documents. NASA provides a much heavier precedent for requirements-to-verification traceability, but its classification-dependent assurance obligations should not be imported wholesale into this workflow. A short criterion→work→evidence mapping is the proposed adaptation, not a NASA requirement for ordinary agent work. ([NASA software engineering requirements, §3.12](https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=Chapter3); [Google documentation ownership and canonical sources](https://abseil.io/resources/swe-book/html/ch10.html))

## Approval, readiness and correctness answer different questions

**Sourced practice:** Rust explicitly separates accepting an RFC from assigning implementation or guaranteeing delivery. OpenSpec likewise does not make verification an absolute prerequisite to archival. The local planner already separates design approval from a complete handoff and from permission to publish, deploy or perform destructive operations. These distinctions prevent a reviewed document, checked task list or archived change from being mistaken for a verified result. ([Rust RFC lifecycle](https://github.com/rust-lang/rfcs/blob/main/README.md); [OpenSpec workflows](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/workflows.md); [Current planner](../agents/planner.md))

**Recommended readiness rule:** “design approved” means the person accepted the reviewed intent and consequential choices; “ready to execute” means the agent specification exists, its dependencies and permissions are explicit, its baseline is revalidated, and no blocking contradiction or decision remains for the affected work. “Implemented” means the changes exist; “verified” requires actual acceptance evidence; release authorization remains separate. A spec can be ready while execution is still waiting on a clearly identified prerequisite, but the handoff must state that limit rather than implying unconditional permission to start. Historical test results remain historical evidence, never a fresh pass.

**Recommended change rule:** implementation refinements that preserve approved outcomes, constraints and consequential choices can update the agent specification without reopening the whole design. Discoveries that alter approved behavior, scope, compatibility, architectural commitments or material risk should pause affected work and return a concise decision delta for reapproval. Preserve the original approval and identify the revised version; do not edit the approved brief retroactively to bless whatever was built. This adapts the planner's existing escalation rule and published practices of updating designs as implementation teaches new facts. ([Current planner](../agents/planner.md); [Ubl, implementation and iteration](https://www.industrialempathy.com/posts/design-docs-at-google/))

**Recommendation:** distinguish defects against agreed intent from requested changes to intent. Correct defects and verify them against the existing contract; review intent changes and reconcile the owning requirements, design, tasks and tests. A disagreement between code, tests and the approved brief is a reconciliation problem—not permission for an agent to choose its preferred authority. Spec Kit's evolving-spec guidance and OpenSpec's explicit deltas are useful models, while narrow decision records can preserve consequential reasoning without proliferating full proposals. ([Spec Kit, evolving specs](https://github.github.io/spec-kit/how-to/evolving-specs.html); [OpenSpec concepts](https://raw.githubusercontent.com/Fission-AI/OpenSpec/main/docs/concepts.md); [Nygard, architecture decision records](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions))

## Keep the process proportional and the maintenance promise explicit

**Sourced practice:** Birgitta Böckeler distinguishes spec-first development from spec-anchored development, where specifications remain maintained contracts, and spec-as-source, where humans edit specifications rather than generated code. Her bounded 2025 trials also describe excessive document volume, brownfield misunderstandings and agents ignoring instructions. These observations do not establish failure rates, but they undermine the assumption that longer specs guarantee control. Google design guidance, Rust's substantial-change threshold and Kiro's lighter paths likewise support tailoring process to the change. ([Böckeler, Understanding spec-driven-development](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [Rust RFC scope](https://github.com/rust-lang/rfcs/blob/main/README.md); [Kiro best practices](https://kiro.dev/docs/specs/best-practices/))

**Recommendation:** within the current planner's mandatory two-stage contract, let an obvious, reversible change use a short human brief and a short separate execution spec. Expand design alternatives, coordination, migration and independent assurance only when ambiguity or risk warrants them. Use bounded implementation slices rather than pretending the whole project can be specified conclusively up front. Repository observations should be labeled as existing facts, distinct from requested changes, so research does not accidentally become an instruction to duplicate existing functionality. ([Current planner](../agents/planner.md); [Böckeler's brownfield observations](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html))

The maintenance model remains a **user decision**. A change-scoped package can retain approved decisions and evidence, then archive its obsolete task instructions. A maintained feature contract instead needs an owner and an expectation that behavior changes update the contract alongside code and tests. Both need clear authority and supersession; only the latter commits to ongoing feature-spec upkeep. A canonical directory, approval-version binding format, risk threshold and evidence standard also remain undecided. Start by evaluating the proposed structure on one moderately ambiguous change, observing review effort, clarification rounds, unplanned scope changes and acceptance failures; this is a suggested pilot, not a measured benefit or authorization to proceed.

## Conclusion

The useful unit of improvement is **an auditable handoff**, not the number of documents generated. A human should be able to understand and approve the consequential choices without reviewing worker mechanics; an agent should be able to execute a bounded assignment without reconstructing the conversation. The next design discussion can therefore focus on how to bind intent, readiness and evidence—and whether specifications remain living contracts—rather than recreating the two-stage boundary the planner already has.
